# 다른 서비스로 범용성 확인

Wetrun 실행기는 서비스 이름을 모르게 만들었다(서비스 고유 내용은 워크플로 YAML에만). 이 설계가 Immich 밖에서도 통하는지 확인하려고, **Immich와 일부러 가장 다른 서비스**를 골라 시험했다. 비슷한 서비스(예: Paperless)에서 통과해도 범용성 근거가 약하기 때문이다.

- 시험일: 2026-11-16~17
- 환경: desktop Linux (Ubuntu 26.04, Docker 29.1, Compose 2.40, restic 0.18.0)
- 재현: 각 폴더의 `setup.sh` → `set -a; . ./secrets.env; set +a; wetrun run workflow.yaml`. 값은 모두 시험 전용이다.

## 무엇이 다른가

| 축 | Immich (기준) | Gitea | Nextcloud |
|---|---|---|---|
| DB | PostgreSQL, 덤프 | **SQLite, 데이터 폴더째** | **MariaDB**, 덤프 |
| 데이터 경로 | 환경 변수(`UPLOAD_LOCATION`) | **compose에 `./data`로 고정** | compose에 `./html`로 고정 |
| 파일 소유자 | 상관없음 | 실행 사용자(1000) | **www-data(33)**. 일반 사용자는 백업조차 못 함 |
| 로그인 | JSON → 토큰 | 토큰 헤더 | **Basic 인증 + 접속 주소 검사(trusted domains)** |
| 데이터 확인 | 내장 `ref_files` (API가 체크섬을 줌) | **`script`**: 최신 커밋 해시와 파일 대조 | **`script`**: WebDAV로 받아 해시 대조 |

## 결과 [측정]

|---|---|---|---|---|
| Gitea | 정상 | `pass` | 커밋 해시와 파일 2개 일치 | 9초 |

| | SQLite DB 삭제 | `fail` | `repo`: HTTP 401 (새로 설치된 빈 Gitea) | |

모든 실행 뒤 남은 컨테이너는 0개였다. Immich(정상 1, 고장 4)까지 합치면 **서비스 3개, 정상 3개, 고장 11개가 모두 기대대로** 나왔다.

## 시험하며 찾은 것

### 1. 데이터 경로가 compose에 고정된 서비스는 복원 데이터가 붙지 않았다 → 고침 (#47)
Gitea 공식 compose는 `./data:/data`처럼 상대 경로를 쓴다. Wetrun은 상대 경로를 실행 디렉터리 기준으로 풀어서 **빈 폴더**가 붙었다. Gitea가 새로 설치된 빈 상태로 떠서 HTTP 401이 났다. **백업은 멀쩡한데 `fail`이 나온 것이다.** Immich는 경로를 환경 변수로 받아서 드러나지 않았다.
→ `compose.project_dir`를 추가했다. 백업을 compose 폴더에서 만들었다면 `"{restore}"`, 백업 경로가 `/src/html`이면 `"{restore}/src"`처럼 지정한다. 실행 디렉터리 밖은 거부한다.

### 2. 복원 절차가 서비스마다 다르고, YAML의 `exec`로 충분했다
Nextcloud는 복원 후에 해야 할 일이 있었다. 모두 `exec` 단계로 처리했고, 실행기 코드는 바꾸지 않았다.
- **파일 소유자를 www-data로 되돌림:** 일반 사용자로 복원하면 소유자가 바뀐다(#20). 컨테이너 안 root로 `chown`한다.
- **유지보수 모드 해제:** 공식 백업 절차대로 유지보수 모드를 켠 채 백업했기 때문이다.
- **검사 주소를 허용 목록에 추가:** 아래 3번

### 3. 내장 `http` 검사는 요청 헤더를 바꿀 수 없다 (한계)
Nextcloud는 허용된 주소(trusted domains)로 들어온 요청만 받는다. 검사 컨테이너의 주소(`http://app/`)는 목록에 없어서 `ready`가 HTTP 400으로 **`fail`**이 났다. 이것도 백업 문제가 아니다. 복원본에서만 `occ config:system:set trusted_domains`로 주소를 추가해 해결했다. `http` 검사에 `headers` 설정이 있으면 더 간단하다(검증 담당 검토 사항).

### 4. `script` 검사는 계약을 직접 지켜야 한다
처음 쓴 Gitea 검사 스크립트는 서비스가 응답하지 않을 때(시간 초과)를 "검사 중 예외"(`error`)로 처리했다. 계약상 **마감까지 서비스가 응답하지 않으면 `fail`**이다. 그래서 Git 객체 손상이 `error`로 나왔다. 스크립트를 고친 뒤에는 `fail`이 나왔다. 내장 검사는 `_common.py`가 이 규칙을 지켜 주지만, 사용자 정의 검사는 작성자가 지켜야 한다.

### 5. 백업 쪽에서 드러난 것 (Wetrun 밖)
- Gitea의 `data/ssh`는 root 소유(0700)라 일반 사용자 백업에서 빠졌다. 시험에는 영향이 없었다(SSH 호스트 키는 다시 만들어진다).
- Nextcloud 파일은 www-data 소유라 일반 사용자는 백업조차 못 했다. 실제 운영처럼 root 권한으로 백업했다.
- MariaDB 클라이언트는 SQL 오류가 나면 기본으로 실패 코드를 낸다. psql(Immich)처럼 `ON_ERROR_STOP`이 따로 필요하지 않았다.

### 6. 데이터를 이름 있는 볼륨에 두는 서비스는 복원 데이터가 붙지 않았다 → 고침 (#48)
위 Nextcloud 시험은 데이터를 호스트 폴더(bind 마운트)에 두는 방식이었다. 그런데 Nextcloud 공식 예시를 포함한 많은 compose는 **이름 있는 볼륨**(`nextcloud:/var/www/html`)을 쓴다. 이 방식([nextcloud-volume/](nextcloud-volume/))으로 다시 시험했다.

| 시도 | 결과 | 이유 |
|---|---|---|
| 그대로 | `fail` (**거짓 실패**) | Wetrun이 볼륨을 빈 것으로 새로 만들어서 복원 데이터가 전달되지 않았다. Nextcloud가 "설치 안 됨" 상태로 떴다 |
| compose 덮어쓰기 파일로 볼륨 자리에 복원 폴더를 붙임 (원리 검증) | `pass` | 같은 대상 경로의 마운트를 덮어쓴다. 코드 변경 없이 원리를 먼저 확인했다 |
| `compose.volumes: {nextcloud: "{restore}/src/html"}` (구현) | `pass` (31초), 사진 삭제 고장은 `fail` | Wetrun이 지정한 볼륨의 마운트를 복원 폴더로 바꿔 붙인다. 지정하지 않은 볼륨(`db`)은 빈 볼륨 그대로라 덤프 복원과 맞는다 |

검토한 다른 방법은 "컨테이너만 만들고(`docker compose create`) 복원 폴더를 볼륨에 복사한 뒤 기동"이었다. 서비스가 진짜 볼륨을 쓰므로 운영과 가장 같지만, 데이터를 한 번 더 복사해 시간과 디스크가 두 배로 든다. 복원 폴더를 바로 붙이는 방식으로 충분해서 채택하지 않았다.

## 판단과 한계

- **실행기는 코드 변경 두 개(`project_dir`, `volumes`)로 세 서비스, 두 가지 저장 방식(호스트 폴더, 이름 있는 볼륨)을 모두 처리했다.** 서비스별 차이(DB 종류, 복원 절차, 확인 방법)는 모두 YAML과 `script`로 해결했다. 실행기 코드에 서비스 이름이 들어가지 않았다.
- **설정이 틀리면 `fail`로 나올 수 있다**(1·3번). 백업 문제와 설정 문제를 Wetrun이 스스로 구별하지 못하는 경우다. 새 서비스의 워크플로는 정상 백업으로 먼저 `pass`가 나오는지 확인한 뒤 써야 한다.
- 시험한 데이터는 작다(파일 2~5개). 고장 탐지는 기능이 동작한다는 입증이지, 실제 운영 탐지율을 증명하는 것은 아니다.
