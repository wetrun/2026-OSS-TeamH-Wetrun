# 인원별 handoff

각자 맡은 일, 일정, 완료 기준, 다른 사람과 맞물리는 지점을 정리한 문서.
작업을 시작하기 전에 자기 파일과 이 문서를 읽는다. 진행하며 바뀐 내용은 각자 파일에 갱신한다.

| 담당 | 역할 | 파일 |
|---|---|---|
| 차은호 | 실행기 | [runner.md](runner.md) |
| 조정민 | 검사·출력 | [checks.md](checks.md) |
| 정순준 | 환경·성능·사용자 평가·문서 | [env.md](env.md) |
| 김영모 | 테스트·평가 | [test.md](test.md) |

## 공통 배경

### 목표

기존 restic 백업으로 Docker Compose 서비스를 운영과 분리된 환경에 복구하고,
로그인·조회·다운로드 같은 사용자 동작으로 "실제로 다시 쓸 수 있는지"를 판정한다. 첫 대상은 Immich.

### 교수님 피드백과 대응

1. **사진 전체를 복원·검증하는 부담, 검증 주기** → 계층형 검증
   - L0: DB의 원본 경로 목록 ⇄ 스냅샷 파일 목록 대조. 사진 본문을 읽지 않음 (매 백업)
   - L1: DB만 복원해 서비스 기동 + 기준 사진 로그인·조회·다운로드·해시 (주 1회, 업데이트 직후)
   - L2: 매 회차 다른 원본 N장만 `restic dump`로 받아 DB checksum과 비교. K회에 전체를 한 번씩 (L1과 함께)
   - L3: `restic check --read-data-subset=n/12`로 저장소를 나눠 검사 (월 1회)
   - 사용자가 `max_bytes`·`max_minutes` 예산을 정하면 그 안에서 샘플 수를 정함
2. **다른 서비스로 일반화** → 실행기(`wetrun/`)에는 서비스 고유 로직을 두지 않고,
   서비스별 내용은 `profiles/<서비스>/`의 YAML과 검사로만 추가. 두 번째 서비스(Paperless-ngx)를
   실행기 수정 없이 붙여 증명. CI가 `wetrun/`의 `immich` 단어를 금지한다.

| 단계 | 기간 | 완료 기준 |
|---|---|---|
| M0 준비하고 손으로 복구해 보기 | 11/3 ~ 11/6 | 수동 복구 성공, 검사 컨테이너 계약 확정 |
| M1 자동으로 한 바퀴 돌리기 | 11/7 ~ 11/12 | `wetrun run` 한 번으로 통과/실패 판정, 실패해도 자원이 남지 않음 |
| M2 가볍게, 다른 서비스도 되게 | 11/13 ~ 11/18 | L0가 원본 누락 탐지, L2가 예산 안에서 동작, Immich 로직이 실행기 밖에만 있음 |
| M3 알아서 돌게 하고 개발 마감 | 11/19 ~ 11/22 | 무인 예약 실행, 실패 시 알림, 운영 데이터 변경 없음. **11/22 실행기 코드 동결** |

### 사람 사이 의존

```
환경(수동 복구 문서, testenv) ──▶ 실행기·검사 개발 시작 (M1)
실행기 ◀── 검사 컨테이너 계약 ──▶ 검사          (M0에 합의)
테스트(고장 백업 5종) ──▶ 평가 (M4)
환경(대용량 데이터셋) ──▶ 성능 측정 (M4)
```
