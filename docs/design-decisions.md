## 0. 전체 흐름

Wetrun은 기존 restic 백업으로 서비스를 운영과 분리된 환경에 **실제로 다시 띄워 보고**, 사용자가 쓰는 방식으로 동작하는지 확인한다.

```
restore → up(DB) → exec(덤프 복원) → up(전체) → 검사 컨테이너(http, ref_files …) → 정리
```

설계의 축은 두 가지다.

1. **판정의 정확성:** 백업이 망가졌으면 `fail`, 도구나 환경 문제면 `error`. 둘을 섞지 않는다.
2. **운영 보호:** 검증 때문에 운영 서비스가 영향을 받으면 안 된다.

아래 결정은 대부분 이 둘 중 하나에서 나왔다.

## 1. 판정 원칙: `fail`과 `error`를 나누는 기준 (#13)

**문제**
README의 완료 조건은 "DB 덤프 손상, 사진 누락, 필수 설정 누락을 모두 실패로 판정"이다. 그런데 이 고장들은 검사까지 가기 전에 실행기 단계(복원, 기동, 명령 실행)에서 먼저 드러난다. 계약에는 검사 단계의 판정만 정해져 있었다.

**왜 중요한가**
`fail`이면 사용자는 백업을 고치고, `error`면 환경을 고친다. 둘이 섞이면 사용자가 엉뚱한 곳을 고친다. 거짓 실패 알림이 반복되면 사용자가 알림을 무시하게 되고, 결국 진짜 고장을 놓친다.

**결정**
원인이 백업 내용에 있으면 `fail`, 실행 환경이나 입력에 있으면 `error`.
- 실행기는 서비스를 모른다(서비스 이름을 코드에 쓰지 않는다는 규칙).
- 하지만 실패에 어떤 자원이 관여했는지는 안다: 저장소, 디스크, Docker, 워크플로 파일, 복원된 파일.

**실험으로 확인한 것 [측정]**

restic 0.19.1의 종료 코드다.

| 상황 | 종료 코드 |
|---|---|
| 비밀번호 틀림 | 12 |
| 저장소 없음 | 10 |
| 스냅샷 없음 | 1 |
| 데이터 손상 (pack 파일 1바이트 변경) | 1 |

CI에서 restic 0.18.0으로도 같은 판정이 나오는 것을 확인했다(#19).

데이터 손상과 디스크 부족 같은 환경 문제가 둘 다 1이라 **종료 코드만으로는 구별할 수 없다.** 그래서 복원 전에 환경 원인(저장소 접근, 비밀번호, 디스크 공간)을 먼저 확인해서 걸러 내고, 그 뒤에 난 복원 실패를 `fail`로 본다.

**고민한 경계 사례**

| 사례 | 판정 | 이유 |
|---|---|---|
| 스냅샷 없음 | `fail` | 검증할 백업이 없다는 건 백업이 만들어지지 않고 있다는 뜻이다. 태그를 잘못 쓴 경우도 같아지므로 메시지에 태그 값을 보여 준다 |
| `{restore}` 안의 파일 없음 | `fail` | 복원 전에는 경로가 없어 미리 검사할 수 없다. 복원 후에도 없으면 백업에서 빠진 것이다 |
| 메모리 부족으로 서비스가 죽음 | `error` | 7절 참고 |

## 2. 검사 시간 제한: 누가 언제 끊나 (#12)

**문제**
서비스가 끝내 뜨지 않으면 검사는 계속 기다린다. 그래서 시간 제한이 있다. 그런데 검사와 실행기가 각자 시간을 재고, 그 사이에 컨테이너 기동 시간이 끼어 있다. 실행기가 먼저 끊으면 "서비스가 안 뜸"(`fail`)이 "검사가 멈춤"(`error`)으로 잘못 기록된다.

**선택지**

| | 검사가 끝내는 시점 | 실행기가 끊는 시점 | YAML `timeout: 120`의 뜻 |
|---|---|---|---|
| (a) 검사가 여유를 뺌 | `timeout − 여유` | `timeout` | 서비스는 실제로 120초보다 짧게 기다림 |
| **(b) 실행기가 여유를 더함 (채택)** | `timeout` | `timeout + 30` | 서비스를 120초 기다림 |

**채택 근거**
1. 사용자가 쓴 숫자와 실제 동작이 같다.
2. 여유 값은 실행기만 알면 된다.
3. (a)는 `timeout`이 작으면 마감이 음수가 된다.

**여유를 10초에서 30초로 늘린 이유 [판단]**
- 여유가 짧으면 정상 서비스도 `error`가 된다(거짓 실패).
- 여유가 길면 늦어지는 것은 검사 자체가 멈춘 경우의 감지뿐이다.
- 피해가 비대칭이므로 느린 기기를 감안해 넉넉하게 잡았다.

## 3. 기본값을 정하는 원칙: "틀렸을 때 피해가 작은 쪽" (#12)

**문제**
시간 제한 기본값(300초)과 메모리 상한 기본값의 근거를 물었을 때 답이 "어림수"였다. 측정으로 정하려 해도, 소요 시간은 실행 환경(디스크, CPU, 원격 저장소, 저사양 NAS)에 따라 몇 배씩 달라진다. 팀 컴퓨터에서 잰 값은 다른 환경에서 근거가 되지 못한다.

**결정**
기본값은 측정이 아니라 **틀렸을 때의 피해**로 정한다.

| | 너무 작으면 | 너무 크면 |
|---|---|---|
| 시간 제한 | 정상 백업인데 실패. 거짓 알림 | 멈춘 실행을 늦게 앎 |
| 메모리 상한 | 정상 서비스인데 강제 종료 | 운영 보호가 약해짐 |

두 경우 모두 작은 쪽이 더 나쁘다. 그래서 기본값은 넉넉하게 잡고, 환경에 맞는 값은 워크플로에서 직접 쓴다. 팀 측정은 "가장 느린 환경에서도 기본값이 충분한가"를 확인하는 용도로만 쓴다.

## 4. 실행 이력으로 시간 제한 자동 조정: TCP RTO 추정 적용 (방향만 확정)

**발상**
TCP는 왕복 시간(RTT)이 계속 변하는 네트워크에서 재전송 타이머를 정한다(RFC 6298). 환경마다 소요 시간이 다른 Wetrun의 문제와 구조가 같다.

```
Est ← 0.875·Est + 0.125·duration
Dev ← 0.75·Dev  + 0.25·|duration − Est|
timeout = clamp(Est + 4·Dev, 하한, 상한)
```

| TCP | Wetrun |
|---|---|
| SampleRTT | 그 단계에 걸린 시간 |
| Karn 알고리즘: 재전송한 세그먼트는 표본에서 제외 | 시간 초과로 끊긴 실행은 표본에서 제외. 실제로 얼마나 걸렸을지 모르므로 |
| 타임아웃이면 RTO 2배 | 끊긴 다음 실행은 timeout 2배 |

**적용 범위에서 고민한 것**
- **복원(`restore`)과 명령 실행(`exec`)에만 쓴다.** 이 단계의 시간 제한은 멈춤을 잡는 안전장치일 뿐이다.
- **검사와 기동(`up`)에는 쓰지 않는다.** 여기서 시간 제한은 판정 기준이다("120초 안에 응답 없으면 fail"). 관측값을 따라 늘어나면, 서비스가 점점 느려지는 문제를 도구가 따라 늘어나며 가린다. 대신 같은 공식으로 **"평소보다 느림" 경고**만 남긴다. 판정은 바꾸지 않는다.
- **이력 저장은 확정했다.** 형식과 "시간 초과로 끊김" 표시 필드는 리포트 담당과 정할 예정이다.

## 5. 검사 컨테이너의 실행 사용자 (#11)

**문제**
검사 컨테이너를 권한이 가장 낮은 `nobody`로 띄우려 했다. 그런데 실행기가 넘기는 설정 파일에는 비밀번호가 있어 실행기 사용자만 읽게(0600) 만든다.

**실험 [측정]**
Docker 볼륨으로 확인했다. uid 65534(`nobody`)는 0600 파일 읽기와 0755 폴더 쓰기 모두 `Permission denied`였다. 소유자 uid는 둘 다 성공했다. macOS Docker는 권한 검사가 느슨해서 개발 중에는 드러나지 않고, Linux와 WSL2에서만 깨진다.

**선택지**

| 선택지 | 문제 |
|---|---|
| `nobody` 유지 + 권한 열기 | 실행 디렉터리(0700) 덕분에 비밀은 안전하다. 하지만 파일마다 권한을 맞춰야 하고, 검사가 만든 파일의 정리가 복잡해진다 |
| 비밀 값만 환경 변수로 넘기기 | 결과 파일 쓰기 문제는 그대로 남는다 |
| **실행기와 같은 uid (채택)** | 권한 제거, 읽기 전용 루트, 외부 통신 차단은 그대로라 잃는 격리가 거의 없다. root로 실행되면 `nobody`로 낮춘다 |

## 6. 실제 Immich로 끝까지 돌리며 찾은 문제 [측정]

단위 시험으로는 드러나지 않고, 실제 서비스를 띄웠을 때만 나온 문제들이다. **실제 서비스로 시험해야 하는 이유를 보여 주는 사례**로 보고서에 쓸 만하다.

| # | 증상 | 원인 | 대응 |
|---|---|---|---|
| 1 | 마운트한 파일이 빈 폴더 | VM 안에서 도는 Docker(Colima 등)는 공유하지 않은 경로를 **오류 없이 빈 폴더로** 마운트한다 | 실행 전에 Docker가 실행 디렉터리를 실제로 보는지 확인하고, 못 보면 `error`로 멈춘다. 대응하지 않으면 정상 백업이 데이터 없음으로 `fail`이 된다 |
| 2 | `.env`를 못 찾음 | 공식 compose의 `env_file: .env`는 실행 디렉터리 기준으로 풀린다 | 워크플로의 `env_file`을 같은 이름으로 복사한다(0600) |
| 3 | 격리 규칙 위반 | 공식 compose의 `/etc/localtime:ro` 마운트 | 아래 7절 |
| 4 | **정상 덤프가 `fail`** | `ON_ERROR_STOP`을 켜면 `pg_dumpall --clean` 덤프의 "접속 사용자 삭제" 줄에서 멈춘다 | 그 두 줄만 걸러 내고 복원한다. 정상 덤프는 통과하고 손상 덤프는 `fail`인 것을 확인했다 |
| 5 | 서버가 종료 코드 137 | 메모리 부족(전역 OOM) | 아래 8절 |

**최종 결과**

| 백업 | 결과 | 시간 |
|---|---|---|
| 정상 | `pass` | 70~80초 (복원 3, DB 기동 6, 덤프 복원 27~42, 전체 기동 32, 응답 1) |
| DB 덤프 손상 | `fail` | psql 종료 코드 3, 오류가 난 줄 위치가 근거로 남음 |
| DB 덤프 누락 | `fail` | 입력 파일 없음 |

세 경우 모두 남은 컨테이너와 폴더는 0개였다.

## 7. 원본 보호 규칙의 예외: 시간대 파일 (#17)

**문제**
"실행 디렉터리 밖 마운트는 금지"라는 규칙이 Immich 공식 compose의 `/etc/localtime:/etc/localtime:ro`를 막았다.

**선택지**

| 선택지 | 장단점 |
|---|---|
| 규칙 유지, 전용 compose를 따로 쓰게 함 | 안전하지만 공식 compose를 그대로 쓸 수 없다 |
| 그 마운트를 지우고 실행 | 동작하지만 컨테이너 시간대가 UTC로 바뀌어 운영과 달라진다 |
| **정해진 파일만, 읽기 전용일 때만 허용 (채택)** | `/etc/localtime`, `/etc/timezone` 두 개만 허용한다. 읽기 전용이라 운영에 쓸 수 없고, 내용도 시간대뿐이다. 쓰기 가능하게 마운트하면 그대로 거부한다 |

허용 목록 방식이라 규칙이 넓어지지 않는다. 예외는 코드와 시험에 명시했다.

## 8. 자원 문제: 검증은 서비스 하나만큼을 더 쓴다 (#13, #17)

**문제**
검증은 운영 서비스 옆에 같은 서비스를 하나 더 띄운다. 메모리 8GB인 Docker VM에서 다른 컨테이너와 함께 돌리자 검증용 Immich 서버가 메모리 부족으로 죽었다. 이것은 피할 수 없는 구조적 비용이다.

**더 큰 위험의 발견 [측정]**
이때의 OOM은 VM 전체 메모리가 바닥난 경우(`global_oom`)였다. 리눅스 커널은 이때 **아무 프로세스나** 골라 죽인다. 운 나쁘면 운영 서비스가 죽을 수 있었다. 자원이 부족한 것보다 "원본 보호" 원칙 위반이 더 심각하다고 판단했다.

**측정한 메모리 [측정]**

| 서비스 | 메모리 | 검증에 필요? |
|---|---|---|
| immich-server | 760MB | 필요 |
| immich-machine-learning | 650MB | 불필요 |
| database | 386MB | 필요 |
| redis | 7MB | 필요 |

**결정 (우선순위 순)**
1. **운영 보호:** 검증 서비스마다 메모리 상한(기본 2GB, 워크플로에서 변경)을 둔다. 넘치면 검증 컨테이너만 죽는다.
2. **정확한 판정:** 메모리 부족으로 죽어서 실패한 단계는 `fail`이 아니라 `error`로 둔다. 백업 문제가 아니기 때문이다.
3. **사용량 줄이기:** 검증에 필요 없는 서비스(Immich의 ML)를 띄우지 않는다. 약 1.8GB에서 약 1.15GB로 **35% 줄었고**, ML 없이도 끝까지 통과하는 것을 확인했다.
4. **운영 안내:** 운영 서버가 빠듯하면 별도 컴퓨터에서 검증하도록 안내한다. 실제 재해 때도 다른 컴퓨터로 복구하게 되므로 오히려 더 현실적인 시험이다.

**남은 한계**
서비스마다 상한을 둘 뿐 합계는 묶지 않는다. 합계가 넘치면 여전히 전역 OOM이 날 수 있다.
- 검토한 대안: 상한 합계를 시작 전 빈 메모리와 비교하는 방법. 기본 상한 2GB × 4개 = 8GB라서 메모리 8GB인 개발 환경(macOS Colima)에서는 항상 거부된다. 즉 거짓 `error`가 나므로 채택하지 않았다.
- 보완 계획: 상한이 아니라 **실행 이력의 실제 최대 사용량**으로 시작 전 여유를 확인한다(4절의 이력 활용).

## 9. 개발 과정에서 고친 도구 문제

- **로컬 검사와 CI의 불일치:** 문서에는 `make lint`가 "CI와 같은 검사"라고 되어 있었다. 그런데 CI에만 "실행기 코드에 서비스 이름 금지" 검사가 있었다. 그래서 로컬에서 통과한 코드가 CI에서 실패했다(주석에 서비스 이름을 쓴 경우). 검사를 `make lint`로 옮기고 CI가 `make lint`를 그대로 쓰게 해서, 다시 어긋날 수 없게 했다 (#18).
- **잘못된 설치 안내:** 온보딩은 Ubuntu apt로 restic을 설치하라고 했다. 그러면 0.16 이하가 설치된다. testenv와 실행기 판정은 0.17 이상의 종료 코드에 기대므로, 릴리스 0.18을 받도록 고쳤다 (#18).

## 10. 예약 실행과 중복 실행 방지 (#29, #31)

**리포트 위치: 실행한 폴더 대신 고정 위치**
- 처음 제안은 명령을 실행한 폴더 기준 `runs/`였다.
- 예약 실행은 실행 폴더가 매번 다를 수 있고, 리포트가 한곳에 쌓여야 실행 이력(4절)으로 쓸 수 있다. 그래서 `~/.local/share/wetrun/runs/`로 정했다.

**예약 실행: 설정을 대신 설치하지 않고 crontab 줄만 만든다**
- 사용자의 시스템 설정(crontab)을 도구가 직접 바꾸지 않는다. 출력된 줄을 사용자가 붙여 넣는다.
- cron은 환경이 거의 비어 있다. 그래서 PATH, 비밀 값 파일, 로그 위치를 줄 안에 넣는다.
- 비밀 값 파일은 다른 사람이 읽을 수 있는 권한이면 거부한다.
- 검증 방법 **[측정]**: Linux에서 `env -i`로 환경을 비운 채 만든 줄 그대로 실행해서 통과했다.
- systemd timer는 만들지 않았다. 필요해지면 같은 명령으로 만들 수 있다.

**중복 실행 방지: 워크플로별 잠금(flock)**
- 실행마다 Compose 프로젝트 이름이 달라서, 겹쳐도 자원 충돌은 없다. 다만 같은 백업을 동시에 두 번 검증하면 자원만 두 배로 쓴다.
- 잠금 파일은 리포트 폴더가 아니라 임시 폴더에 둔다. 처음에는 리포트 폴더 옆에 뒀는데, "리포트 폴더가 망가져도 판정은 유지" 시험이 잠금 단계에서 먼저 실패했다. 잠금과 리포트 저장은 서로 영향을 주면 안 된다.
- 프로세스가 죽으면 운영체제가 잠금을 풀어서, 남은 잠금 파일 때문에 영원히 멈추는 일이 없다.

## 11. v0.1 목표 확인 (#30) [측정]

README의 첫 목표는 "restic 백업 하나에서 Immich 서비스 전체를 복구하고, 정상 백업과 고장 난 백업을 구별하는 CLI"다. 실제 Linux 기기(Ubuntu 26.04, Docker 29.1.3, restic 0.18.0)에서 Immich 프로필로 확인했다.

| 백업 | 결과 | 판정한 단계와 근거 |
|---|---|---|
| 정상 | `pass`, 53초 | 사진 5개 전부 원본과 해시 일치 |
| 사진 원본 1장 누락 | `fail` | `ref_files`: 원본 다운로드 실패 (HTTP 404) |
| 사진 원본 1장 손상 (1바이트) | `fail` | `ref_files`: 다운로드한 원본이 다른 파일 |
| DB 덤프 손상 | `fail` | `exec`: psql 종료 코드 3 |
| DB 덤프 누락 | `fail` | `exec`: 입력 파일 없음 |

- 모든 실행 뒤에 남은 컨테이너와 실행 디렉터리는 0개였다.
- testenv Immich(운영 역할)를 켜 둔 채로 돌려도 충돌하지 않았다.
- **"서비스가 응답한다"(HTTP 200)만으로는 사진 누락·손상을 잡지 못한다.** 이 두 경우 모두 `ready` 단계는 통과했고 `ref_files`에서만 잡혔다. README의 "HTTP 성공만으로 데이터 복구 성공을 판정하지 않는다" 원칙이 왜 필요한지 보여 주는 결과다.

## 12. 실행이 아예 돌지 않은 경우: 잡지 않기로 함

**문제**
알림은 실행했는데 결과가 실패·오류일 때만 간다. 서버가 꺼지거나 cron이 멈춰 실행 자체가 없으면 아무 연락이 없고, 사용자는 "알림이 없으니 정상"으로 오해할 수 있다.

**검토한 방법**

| 방법 | 서버가 멈춘 경우를 잡나 | 판단 |
|---|---|---|
| 외부 감시 서비스(healthchecks.io 등)에 실행마다 신호 | 잡음 | 외부 서비스에 기대지 않기로 함 |
| 다음 실행 때 "그동안 비었음"을 알림 | 못 잡음 (다시 돌아야 앎) | 사후 기록일 뿐 |
| `wetrun status`로 마지막 실행 시각 확인 | 못 잡음 (사람이 쳐야 앎) | 같은 서버 안의 장치 |
| systemd `Persistent=true`로 놓친 실행 다시 돌리기 | 재부팅 공백만 메움 | 부분 해결 |
| 다른 내 컴퓨터가 리포트 시각 확인 | 잡음 | 사용자가 설정. 문서로 안내 |

**결론**
"무언가가 일어나지 않았다"는 그 일을 하는 주체가 알릴 수 없다. 멈춘 프로그램은 멈췄다고 말하지 못한다. 그래서 이 문제의 근본 해결은 **멈추는 쪽과 독립된 관찰자**뿐이고, 같은 서버 안에서 만든 장치는 서버가 멈출 때 같이 멈춘다.

그래서 Wetrun의 책임 범위를 **"실행되면 결과를 남기고, 실패하면 알린다"** 까지로 정했다. "실행되지 않음"은 사용자 문서에 한계로 적고, 관찰자를 두는 방법(매일 결과 받기, 다른 컴퓨터, 감시 서비스)만 안내한다.

같은 서버 안에서 흉내 내는 기능(위 표의 두 번째·세 번째 줄)은 넣지 않았다. 넣으면 사용자가 "멈춤도 잡아 준다"고 믿게 되어 오히려 위험하다. "HTTP 응답만으로 복구 성공을 판정하지 않는다"(11절)와 같은 원칙이다: **알 수 없는 것을 아는 척하지 않는다.**
